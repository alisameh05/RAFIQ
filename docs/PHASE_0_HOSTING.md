# Zero-cost Phase 0 validation hosting

Use this setup for scheduled RAFIQ university validation with synthetic data. Platform owns setup and access. Release authorizes deployment of the reviewed candidate. Record the operator, independent reviewer, deployment owner and approved operations-store reference in the private handoff. [Provisioning issue #3](https://github.com/alisameh05/RAFIQ/issues/3) · [Deployment issue #11](https://github.com/alisameh05/RAFIQ/issues/11)

## Hosting and cost controls

| Component | Setup | Cost and availability |
| --- | --- | --- |
| Next.js | Reuse the isolated Vercel Hobby project. Have its owner deploy the reviewed web build manually. Use the provider HTTPS URL and verify the project runtime against the TRD before building. | Keep the project on Hobby for this non-commercial validation. Use included quotas and keep paid add-ons disabled. Hobby has no configurable team spend budget. [Hobby plan](https://vercel.com/docs/plans/hobby) · [Manual deployments](https://vercel.com/docs/cli/deploy) |
| FastAPI | Use one Render Free **Web Service** in the approved Hobby workspace with its provider HTTPS URL. Select the reviewed API image by digest when the service form offers Free for that source. Keep deploys attended and disable automatic deploys and previews if offered. | Verify that the workspace has no payment method and the instance selector shows Free. The Hobby allowances are 5 GB outbound bandwidth and 500 Starter build minutes per month. Render Free includes 750 instance hours per workspace per calendar month. On a cardless workspace, bandwidth exhaustion suspends Free services and pipeline exhaustion stops new builds for the rest of the month. [Render Free](https://render.com/docs/free#monthly-usage-limits) · [Build pipeline](https://render.com/docs/build-pipeline#included-minutes) · [Prebuilt images](https://render.com/docs/deploying-an-image) |
| Python/R worker | Start the matching reviewed worker image on a named, attended team host with the validation worker credentials. The worker reaches PostgreSQL over TLS and requires no inbound listener. | Use the existing team host for scheduled validation. Stop the worker after the session using its documented drain procedure. [Docker responsibilities](DOCKER.md) |
| PostgreSQL and private objects | Reuse the validation Supabase Free project for PostgreSQL. If Platform approves Supabase Storage for the synthetic fixture, use a private validation bucket and verify the scoped access path and denial. | Confirm database, storage and egress headroom before each session. Keep files synthetic and small. [Supabase pricing](https://supabase.com/pricing) · [Private buckets](https://supabase.com/docs/guides/storage/buckets/fundamentals) |
| Identity | Reuse the isolated Clerk development instance with approved synthetic accounts and the exact validation origin and redirect URLs. | Development instance limits apply. Use test identities for attended validation. [Clerk environments](https://clerk.com/docs/guides/development/managing-environments) |

## Set up the reviewed candidate

Use the [candidate handoff](PHASE_0_VALIDATION_CANDIDATE.md) to record approval, operator access, rollback and deployed checks.

1. Record the reviewed revision, passing CI run, API and worker image digests, and rollback reference. Confirm provider quotas, operator access and the approved secret store. Keep provider IDs, connection strings, signing secrets and registry credentials in the private handoff.
2. From the approved operator host, run the candidate's one-shot Alembic migration with the migration role. Verify PostgreSQL TLS connectivity from the API and worker hosts under their separate runtime roles. If IPv6 direct connectivity is unavailable, test the included Supabase session pooler before choosing any paid network add-on. [Supabase connection modes](https://supabase.com/docs/guides/database/connecting-to-postgres)
3. Deploy the API with its validation-only runtime configuration. Bind the process to `0.0.0.0` on Render's `PORT` and set the candidate's existing readiness path as the service health check. Expose the minimum readiness response and keep operational details behind the approved access controls. Confirm the API reaches the expected database schema before accepting application traffic. [Render port binding](https://render.com/docs/web-services#port-binding) · [Render health checks](https://render.com/docs/health-checks)
4. Configure the matching Vercel build against the exact API HTTPS origin and Clerk development instance. Allow only the approved browser HTTPS origin in FastAPI CORS, configure Clerk redirects, and register the approved signed test callbacks against the validation API. Start the separate worker and record its heartbeat. Use the approved operations store for server secrets. Browser-visible build configuration contains only the values intended for public delivery.

## Rehearse and handle exhaustion

- Send an attended readiness request before opening the demo browser. Render Free spins down after 15 minutes without inbound traffic and can take about a minute to wake. Measure the actual recovery from idle and confirm the API is ready before starting the smoke test. [Render cold starts](https://render.com/docs/free#spinning-down-on-idle)
- Confirm that a synthetic browser submission produces one durable R result that survives reload. Check unauthenticated and wrong-owner denial, signed callback acceptance and rejection, and private-object access and denial. Record the runtime versions, deploy IDs, readiness and worker heartbeat, test outcomes and remaining owners. [Hosted acceptance](https://github.com/alisameh05/RAFIQ/issues/11)
- If a quota is exhausted, Free is unavailable for the approved source, or provider setup requires billable usage, stop hosted setup and record the blocker. Use the approved local fixture for an attended walkthrough and reschedule hosted verification when the free path is available. [Local fixture](https://github.com/alisameh05/RAFIQ/issues/5) · [Production qualification](https://github.com/alisameh05/RAFIQ/issues/4)
