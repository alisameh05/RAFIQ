## Hosted fixture configuration under review

The validation-specific code is separate from the product identity and media contracts. In `hosted-validation` mode, the API verifies a Clerk session against the configured development issuer, public verification key and exact browser origin, then admits only the two explicitly configured synthetic subjects. Local fixture bearer strings are not accepted in this mode. API, migration and worker database URLs require PostgreSQL `verify-full` TLS and an explicit CA certificate. The API honors the host's `PORT`. The local mode remains for loopback fixtures and must not be exposed as hosted authentication.

Set `NEXT_PUBLIC_RAFIQ_HOSTED_VALIDATION=true`, `NEXT_PUBLIC_RAFIQ_API_ORIGIN` and `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` on the validation web build. Store `CLERK_SECRET_KEY` in the web runtime's private configuration. Set `RAFIQ_MODE=hosted-validation` for the API, migration and worker. The API also needs `RAFIQ_WEB_ORIGIN`, `CLERK_ISSUER`, `CLERK_JWT_KEY`, `RAFIQ_VALIDATION_DRIVER_A` and `RAFIQ_VALIDATION_DRIVER_B`. Keep the approved synthetic subjects and all credentials in the private operator handoff. Session-token verification covers the validation fixture only.

For the existing validation database, review the [one-time role bootstrap](../ops/validation/bootstrap-hosted-database.sql), then execute it as the database owner. It creates the fixture schema and grants the prepared validation roles their separate privileges. Release enables the three logins and supplies `RAFIQ_MIGRATE_DATABASE_URL`, `RAFIQ_API_DATABASE_URL` and `RAFIQ_WORKER_DATABASE_URL` only to their respective processes. Run `alembic upgrade head` from the exact API image with the migration role before starting the API and worker. Check `0003_validation_callback` and the effective login on each host.

The validation-only `/validation/webhooks/clerk` endpoint verifies a signed event from the configured development instance and records only its delivery ID and body digest. Duplicate deliveries are idempotent; conflicting reuse is rejected. It is a callback transport probe, not the product `/webhooks/clerk` lifecycle reconciler. Configure its signing secret through the approved vault and register it only against the development instance after the HTTPS origin exists.

The private-object gateway uses `RAFIQ_STORAGE_ORIGIN` and `RAFIQ_STORAGE_PUBLISHABLE_KEY`. Configure Clerk third-party authentication in the isolated Supabase project, then apply the [validation Storage policy](../supabase/migrations/20261126232258_validation_private_object.sql). Insert the approved development issuer and synthetic subjects in `rafiq_validation.object_subjects` through the operator procedure. Seed each subject's `private-access-check.txt` in the private validation bucket and record its expected digest. From the deployed API prove allowed access, anonymous denial and wrong-owner denial. The gateway enforces owner checks, caps returned bytes and accepts only a publishable key.
